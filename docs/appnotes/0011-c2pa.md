# 0011 C2PA provenance across related Sources and Flows

## Abstract

[C2PA](https://c2pa.org/), or "Content Credentials" is a metadata standard for authenticating the origin of media, and describing its provenance.
It uses certificates, cryptographic hashes, digital signatures and a tree of linked "ingredients" - links to the different versions of the assets used to create the current one.
However, as C2PA's hashing mechanism is intentionally brittle, and currently reliant on the container format, it is not obvious to imagine how to preserve provenance data across workflows involving TAMS.
Here we will examine some best practices for ingesting and exporting media from TAMS to allow clients to propagate and re-sign provenance without significant data loss.

This note is an initial recommendation on how to work with C2PA in TAMS for both file-based and live streams.
Implementors are encouraged to feedback and contribute to the recommendation as the workflows and standards develop.

## Trust Principles

One of the key features of C2PA is the description of the "action" taken when the ["hard binding"](https://c2pa.org/specifications/specifications/2.1/specs/C2PA_Specification.html#_hard_binding) (or hash) of content changes, which could be described as a new "version".
This action is important, as it can help differentiate a purely technical change, like repackaging, or transcoding for different bitrates, from more "editorial" ones, like cutting material or overlaying graphics.

TAMS is purely a media store, and has no concept of the type of action performed on content, nor does it perform any actions _itself_.

Instead, all actions are performed by clients of TAMS.
This leads us to our guiding principle for working with C2PA in TAMS: the generation of new C2PA manifests and the associated signatures should be done by TAMS clients, potentially using data stored in TAMS.

TAMS clients writing C2PA data will **need to assume responsibility for the data they write**, which means they will need to consider the broader workflow, including other clients involved in creating the media to be signed.

In situations where the workflow that produced that the Flows and Sources being used occurred outside of the organisation signing the C2PA asset, the signing organisation exposes itself to risk if the workflow turns out to be untrustworthy.
There are a number of ways to handle this, some options are:

1. The signing organisation doing an export asks the external organisations in the workflow to include a signed C2PA manifest with their output Flows and Sources
2. The signing organisation works out-of-band with the external organisations to establish their own expectations and trust, and then signs the whole workflow themselves, assuming all the risk
3. The signing organisation makes a decision to only sign workflows that are in their control, excluding workflows where external organisations are present

## File-based Workflow

Here's an example workflow to help us understand where C2PA validation and signing can happen.

```mermaid
    end
    subgraph Social

```

Fig 1 - Example workflow

We will assume that the contributed video is an MP4 file including a C2PA manifest signed by the External Contributor (or by a device they own).

While out-of-scope for this application note, upon "accepting" this file, it is recommended for the broadcaster to validate the file before ingesting it into their TAMS store.
Validation checks that the signature and hash of the content are cryptographically correct (amongst other things), and also checks that the certificate that signed the manifest is also valid.
This last part can vary, depending on use case, but in the news industry, the certificate can be checked against the [IPTC's "Verified News Publisher" list](https://iptc.org/verified-news-publishers-list/), to ensure the identity of the signer is correct.

### Ingest

Once validated, the broadcaster should upload the contributed MP4 as-is into TAMS, as a single Segment.
This is done to ensure a modification-free record of the initial contribution, which preserves both the C2PA metadata, as well as its binding to the content, which, for a monolithic MP4 file, will be sensitive to any manipulation.

```mermaid
  flowchart LR;
    subgraph ext[External Contributor]
      cap[Captured Video]-->sign-cap{Sign video};
    end
    sign-cap-->validate{Validate video};
    subgraph broadcaster[Broadcaster]
      validate-->tag{Tag with C2PA}
      tag-->cont[Contributed Video #40;Flow#41;]
    end
```

Fig 2 - Ingest process

As part of that upload process, the multi-essence Flow being created should be tagged with `c2pa-provenance: embedded`, to ensure the provenance can be found later at export-time.

Alternatively, depending on workflow and performance constraints, the C2PA manifest can be copied out of the file, and subsequently uploaded to TAMS as a child collected data Flow, with a `role` of `c2pa`, and an `essence_parameters/data_type` value of `application/c2pa` and a `format` value of `urn:x-nmos:format:data`.
If this is done, the multi-essence Flow's tag should instead be `c2pa-provenance: detached`.

```mermaid
  flowchart LR;
    c2pa-data[C2PA manifest data Flow\ndata_type: application/c2pa]-- collected by -->parent[Multi-essence collection Flow\n#40;original video file#41;];
    video[Video essence Flow]-- collected by -->parent;
    audio[Audio essence Flow]-- collected by -->parent;
```

### Editing

In the Figure 1 workflow, the broadcaster edits the contributed video to get it ready for publication on a social media platform.
The example shows two other contributions to the final asset: an intro and outro.
Depending on the level of C2PA adoption in an organisation, these assets may have C2PA provenance data attached themselves.
For this example, we will assume they don't.

The broadcaster continues to edit the package, potentially demuxing and segmenting the contributed video, as well as cutting to length, and combining it with the intro and outro videos.
In this process, no further C2PA-specific actions need to be taken, TAMS is used as-is.
However, there is an assumption that knowledge of the edit graph is captured and retained by something outside of TAMS - this might be a non-linear editor or MAM system.
This will be critical in the next step, where a package is readied for export, and C2PA provenance data is re-added.

### Export

When the broadcaster arrives at the point where they wish to download the final package ready for upload to a social media platform, they will need to perform a number of actions to assemble a new C2PA manifest for the packaged file.

First, the broadcaster should decide the granularity of provenance data they wish to include in the C2PA manifest that will be generated.
For this application note, we will consider a "coarse-grained" approach, where C2PA manifests are not generated for each intermediate step in the edit graph.
However, implementors are free to do so, in which case, they should follow the procedure below for each intermediate step.

The broadcaster (or more likely, the software package the broadcaster is using to interact with TAMS) should generate a graph of the edits performed in order to produce the final package.
They should make a list of the inputs to the final package (which, in this example, includes the contributed video and two-non C2PA videos: intro and outro), as well as the set of edits done (for example: cutting the contributed video, adding the intro and outro, repackaging/muxing, transcoding).
For each of the inputs, the Flow in TAMS should be interrogated to discover whether it has an existing C2PA manifest.

For mono-essence Flows, this can can done by following the `collected_by` relationship (found in the [Flow Details property on Flows](https://bbc.github.io/tams/5.1/index.html#/operations/GET_flows-flowId)) to its collector Flow, to get to the parent multi-essence Flow.

Once at a multi-essence Flow, the `c2pa-provenance` tag should be read to discover whether a C2PA manifests exists, and where it can be read from:

- No Tag: A C2PA manifest has not been identified in this Flow
- `none`: A C2PA manifest is not present inside this Flow
- `embedded`: A C2PA manifest is present inside this multi-essence Flow
- `detached`: A C2PA manifest has been copied from this multi-essence Flow into a collected mono-essence data Flow.
  The Flow will have the role `c2pa` in the multi-essence Flow's `flow_collection` array.

A C2PA manifest can then be constructed by converting inputs and edits into C2PA `ingredients` and `actions` respectively.
For each ingredient that had an available C2PA manifest, the whole C2PA manifest store for that ingredient should be added to the new C2PA manifest being generated.
This step will ensure that the input media with C2PA data is correctly linked so that the whole provenance chain is captured.

Depending on the use case, organisations may wish to include additional editorial metadata as a part of the assets manifest, which, if included, is securely bound to the content in the same way as the edit history.
Such metadata can include vocabularies from [Exif](https://www.cipa.jp/std/documents/download_e.html?DC-008-Translation-2023-E), [IPTC](https://www.iptc.org/std/photometadata/specification/IPTC-PhotoMetadata) and [Schema.org](https://schema.org/), using the [C2PA Metadata assertion mechanism](https://c2pa.org/specifications/specifications/2.1/specs/C2PA_Specification.html#_common_requirements).

Various libraries are now available to help implementors with manifest generation and signing, including the open-source [c2pa-rs](https://github.com/contentauth/c2pa-rs) library in Rust, for which other language bindings are available.

With the C2PA manifest and claim now generated, the manifest should be signed.
The actual certificate used will depend on the implementors use case and industry, but as mentioned previously, news organisations are able to use the Verified News Publisher certificates managed by IPTC, if they wish to sign as an organisation.

The resulting file can optionally be re-imported into TAMS as a multi-essence Flow, following the advice of the [Ingest section](#ingest).

```mermaid
  flowchart LR;
    subgraph broadcaster[Broadcaster]
      cont[Contributed Video #40;Flow#41;]-->clip[Clipped Video #40;Flow#41;];
      clip-->final[Final package #40;Flow#41;];
      intro[Library Intro #40;Flow#41;]-->final;
      outro[Library Outro #40;Flow#41;]-->final;
      final-->assembly{Get manifests from inputs};
      assembly-->manifest-gen{Generate & sign new manifest}
      manifest-gen-->exp[Signed export for social #40;Flow#41;]
    end
    subgraph Social
      exp-->social[Published on social]
    end
```

Fig 4 - Export / Publishing process

Finally, in our example workflow the file is published to a social media platform, which depending on their support, may render provenance user interface for users, allowing them to inspect the secure provenance history.

## Live Workflow

Live workflows using init segments require TAMS 8.2 or later, which supports the `init_object_id` field on Flow Segments. The current version of the C2PA specification applies to content packaged using the ISO BMFF standard (including CMAF). It does not support MPEG Transport Streams. C2PA also defines carriage over Enhanced RTMP, which is not covered here.

The C2PA specification defines two different methods for segment-based validation or "Live Media": the 'Per-segment C2PA Manifest Box' method is [Section 15.4](https://spec.c2pa.org/specifications/specifications/2.5/specs/C2PA_Specification.html#using_c2pa_manifest_box) or the 'Verifiable Segment Info' (VSI) method is [Section 15.5](https://spec.c2pa.org/specifications/specifications/2.5/specs/C2PA_Specification.html#verifiable_segment_info).

Section 15.4 carries a full C2PA Manifest Box in every media segment and does not require session keys. Section 15.5 carries a compact signature per segment, with session keys authenticated by a manifest. It has lower per-segment overhead but depends on the applicable manifest and session-key state being available to the reader. The methods have different validation and continuity rules; readers must identify the profile in use.

### Per-Segment C2PA Manifest Box (Section 15.4)

For live media, every media segment shall contain a C2PA Manifest Store in a top-level [C2PA `uuid` box](https://spec.c2pa.org/specifications/specifications/2.5/specs/C2PA_Specification.html#uuid_box). Its active manifest contains:

* A `c2pa.hash.bmff.v3` assertion with a `hash` field covering the bytes of that segment and no `merkle` field
  * Apply the C2PA BMFF exclusion rules, including exclusion of the C2PA `uuid` box itself
* A `c2pa.livevideo.segment` assertion
  * A monotonically increasing `sequenceNumber` that provides a unique identifier for the segment. Increasing by exactly one is recommended to simplify loss and replay detection
  * A `streamId` that provides a unique identifier for the entire live media stream. This value can be any string that uniquely identifies the stream, such as a UUID. Persist an association between that value and the TAMS Flow
  * A `continuityMethod` which indicates the method used to ensure continuity between segments. This should be set to `c2pa.manifestId`
  * A `previousManifestId` set to the active C2PA manifest identifier of the preceding segment
* Optionally, any other assertions relevant to that segment

Example `c2pa.livevideo.segment` (shown as JSON for readability; the assertion is encoded as CBOR):

```json
{
  "sequenceNumber": 175,
  "streamId": "123e4567-e89b-12d3-a456-426614174000",
  "continuityMethod": "c2pa.manifestId",
  "previousManifestId": "urn:c2pa:F9168C5E-CEB2-4FAA-B6BF-329BF39FA1E4"
}
```

Signing must be the final operation that changes the media segment. Store and later validate the exact signed bytes; concatenating, remuxing or otherwise rewriting them invalidates the C2PA cryptographic binding.

#### TAMS Representation

The corresponding TAMS representation is one mono-essence video Flow. Each signed media segment is stored unchanged as one Media Object and placed on the Flow timeline by one Flow Segment. The Flow Segment's `object_id` identifies the Media Object; C2PA continuity is carried inside the media Objects and is independent of the TAMS timeline.

* `container` set to `video/mp4`
* `essence_parameters.init_segments` set to `true`
* each init segment stored as a TAMS Object
* each Flow Segment's `init_object_id` identifying the Object containing the init segment required to decode that media segment
* the same init Object ID reused until the required init bytes change

For the init-segment workflow described here, each init segment shall contain a C2PA `uuid` box whose `bmff-hash-map` includes the `moov` box and applies the C2PA exclusions, including exclusion of that `uuid` box.
This binds the manifest to the track initialization data.
The init segment must not contain an `mdat` box, as required by [C2PA Section 15.8.1](https://spec.c2pa.org/specifications/specifications/2.5/specs/C2PA_Specification.html#_initialcommon_validation_steps).
This note's TAMS read/write guidance assumes the manifest is available from the referenced init Object.
Create a new init Object when the required init bytes change, for example because decoder configuration changes.
Section 15.4 claim-signer rotation alone does not require a new init segment.

Retain each init Object while any retained media Flow Segment references it. A media Object without its applicable init may be playable with cached decoder configuration but cannot be independently validated using this profile.

```mermaid
flowchart LR
  initA[init Object A]
  initB[init Object B]
  seg0[Media Object 0<br/>C2PA manifest 0]
  seg1[Media Object 1<br/>C2PA manifest 1]
  seg2[Media Object 2<br/>C2PA manifest 2]
  seg3[Media Object 3<br/>C2PA manifest 3]
  initA --> seg0
  initA --> seg1
  initB --> seg2
  initB --> seg3
  seg0 -. previous manifest .-> seg1
  seg1 -. previous manifest .-> seg2
  seg2 -. previous manifest .-> seg3
```

The solid arrows are TAMS references. The dashed arrows are C2PA continuity links embedded in the next Media Object.

An init Object change does not itself start or end a C2PA live stream. If the claim-signing certificate or signing service changes, continue the same `streamId`, sequence and `previousManifestId` chain, and validate the new signer under normal trust policy. A signer change is not a continuity break.

#### Writing to TAMS

Follow this procedure, together with the general storage workflow in [Application Note 0024](https://github.com/bbc/tams/blob/main/docs/appnotes/0024-using-init-segments.md):

1. Create a mono-essence video Flow with `container: video/mp4` and tag it with `c2pa-provenance: embedded` as a discovery hint. Set `essence_parameters.init_segments` to `true`.
2. Start the C2PA signing state with a new `streamId`, initial sequence number and signer. 
3. C2PA-sign each init segment, request storage for it (with `content_type` set to the init segment's MIME type IF the init MIME type differs from the media MIME type), and upload it as an Object. Retain the returned Object ID.
4. For each media segment, generate and sign its final bytes, request storage for a Media Object without setting `content_type`, and upload those exact bytes using the allocated URL and returned content type.
5. Register one Flow Segment with the Media Object ID and exact Flow `timerange`. Include the current `init_object_id`.
6. Reuse that init Object ID for subsequent Flow Segments. Upload and select a new init Object before registering the first media segment that requires changed init bytes.

A simplified example Flow Segment registration:

```json
{
  "object_id": "media-object-id",
  "timerange": "[1700000000:0_1700000002:0)",
  "init_object_id": "init-object-id"
}
```

When `init_segments` is true, every media Flow Segment must identify the Object containing its init segment. A successful upload does not place an Object on the Flow timeline; the Flow Segment registration does that. Conversely, the registration and its timerange are TAMS metadata and are not authenticated by the embedded C2PA manifest.

#### Reading and Validation

A reader validates three separate things: the TAMS representation, each C2PA asset, and continuity between C2PA assets. Validation is stateful even though every media Object is independently signed:

1. Request all Flow Segments covering the desired timerange, following TAMS pagination, and process them in ascending Flow timerange order.
2. Check Flow timeranges for gaps and overlaps according to application policy.
   Read the init Object ID from `init_object.object_id` in each Flow Segment response; `init_object_id` is the registration field.
   When that ID changes, fetch the init Object using `init_object.get_urls`, validate its C2PA manifest and binding, and initialise the decoder before processing the referencing media segment.
3. Download each Media Object without concatenating, remuxing, or rewriting it. Apply normal C2PA manifest, signature, credential, assertion and `c2pa.hash.bmff.v3` validation to those exact bytes.
4. For each media segment after the first one observed, check that `streamId` is unchanged, `sequenceNumber` increases as required, and `previousManifestId` exactly matches the preceding media segment's active manifest identifier.
5. Report TAMS mapping, C2PA validity, C2PA continuity and signer trust separately. A correctly signed Object can be on the wrong TAMS timerange, and a valid signature from an untrusted credential is not a trusted result.

A media segment may have a valid signature and hard binding while continuity from the intended start of the stream is unproven. This occurs, for example, when validation begins mid-stream and the predecessor is unavailable. The reader should report the segment-level result and the chain-anchoring result separately.

Once a validation failure occurs in a linear playback session, later valid segments do not erase it. The client should retain and expose the failure until an explicit discontinuity, seek, or new validation session establishes a new policy boundary.

### Verifiable Segment Info (Section 15.5)

Section 15.5 is an alternative to the per-segment manifest method above. It places a C2PA manifest and session-key assertion in an init segment, then carries a compact, session-key-signed VSI in each media segment. It does not use the Section 15.4 `c2pa.livevideo.segment` assertion or `previousManifestId` chain; validation instead uses the segment sequence, active manifest, and session-key policy.

#### Init segment and session keys

The init segment is ISO BMFF initialization data with a C2PA Manifest Store in a C2PA `uuid` box; it must not contain an `mdat` box. The active manifest's `bmff-hash-map` must cover the `moov` box, binding the manifest and session-key assertion to the track initialization data.

The `c2pa.session-keys` assertion contains one or more entries with:

* `key`: the public COSE key, with a unique `kid`
* `minSequenceNumber`: the first segment sequence allowed for this key
* `createdAt`: a tagged RFC 3339 creation time
* `validityPeriod`: validity duration in seconds
* `signerBinding`: a detached COSE signature made with the session key over the manifest signer's end-entity certificate

Generate session keys using any [C2PA supported algorithm](https://spec.c2pa.org/specifications/specifications/2.5/specs/C2PA_Specification.html#_certificate_profiles).
Keep private keys in the signing service; only publish their public keys.
A reader must validate the init manifest and signer trust, the assertion, and each `signerBinding` before trusting a session key.
The key must not sign a sequence below its `minSequenceNumber`; for BMFF/CMAF, the segment's presentation time must be at or after `createdAt` and no later than `createdAt` plus `validityPeriod`.
Key validity windows may overlap during rotation, but publish the new key before using it.
When introducing new keys in an updated manifest, their `minSequenceNumber` must be greater than or equal to the current segment sequence number, as required by the [C2PA Session Keys requirements](https://spec.c2pa.org/specifications/specifications/2.5/specs/C2PA_Specification.html#session_keys_assertion).
Rotate keys when provenance changes as well as before expiry, and keep the manifest-signing credential lifecycle distinct from the session-key lifecycle.

#### Media segment

Every media segment contains a VSI in an `emsg` box:

| `emsg` field | Section 15.5 value |
| --- | --- |
| `version` | `0` |
| `scheme_id_uri` | `urn:c2pa:verifiable-segment-info` |
| `value` | `fseg` |
| `presentation_time_delta` | `0` |
| `timescale`, `event_duration` | Values covering the whole segment |
| `id` | A session-unique value |
| `message_data` | Encoded `COSE_Sign1_Tagged` VSI |

The COSE object has an attached CBOR `segment-info-map` payload. Its protected header contains `alg` and may contain `iat`; its unprotected header contains `kid`. The payload contains:

* `sequenceNumber`: a unique segment identifier that either matches `mfhd.sequence_number` or follows the applicable [ISO/IEC 23009-9 segment-indexing rules](https://www.iso.org/standard/85639.html). The value increases by one for each subsequent segment; it must not repeat or decrease. The tested implementation matches it to `mfhd.sequence_number`.
* `manifestId`: the identifier of the active manifest from the applicable init segment
* `bmffHash`: a BMFF hash map over the media segment
* optionally, `manifestUri`, a hashed external URI for retrieving a manifest

The BMFF hash excludes C2PA VSI `emsg` boxes to avoid a hash/signature cycle. Its exclusion must identify `/emsg` and match `urn:c2pa:verifiable-segment-info` at byte offset `0`; do not exclude every `emsg`. The VSI segment hash does not use the `merkle` field. Sign after packaging and preserve the resulting bytes unchanged; remuxing, rewriting boxes, or removing the VSI will invalidate the signature.

BMFF hashing includes the absolute byte offset of each included root box, so the hash must use the final post-embedding box layout and offset values, as required by [C2PA Section 16.3.2.2](https://spec.c2pa.org/specifications/specifications/2.5/specs/C2PA_Specification.html#bmff-hash-computation).
Reserve space for the final VSI `emsg` or use a multi-pass process, ensuring the hash reflects the final box positions and any embedded offset fields.
Inserting or resizing an excluded `emsg` after hashing can still invalidate the hash if other hashed boxes move.

#### Writing to TAMS

Follow the storage workflow in [Application Note 0024](https://github.com/bbc/tams/blob/main/docs/appnotes/0024-using-init-segments.md), with the Section 15.5 signing state applied as follows:

1. Create a mono-essence video Flow with `container: video/mp4`, `essence_parameters.init_segments: true`, and the `c2pa-provenance: embedded` discovery tag.
2. Package the stream and establish its sequence numbers before signing. Use `mfhd.sequence_number` or the supported ISO/IEC 23009-9 indexing scheme, and reject missing, repeated, out-of-order, or unexpected values; do not silently renumber signed media.
3. Generate an ephemeral session key and unique `kid`. Set `minSequenceNumber`, `createdAt`, and a `validityPeriod` that covers the expected signing and presentation interval. Create `signerBinding` over the manifest signer's end-entity certificate.
4. Add the public key entry to the `c2pa.session-keys` assertion, build and sign the init manifest, and upload the signed init segment as an Object using the init storage `content-type` rules above. Retain its Object ID and active `manifestId`.
5. For each media segment, establish the final box layout, including the VSI `emsg`, and compute the BMFF hash using post-embedding offsets with the VSI-only `emsg` exclusion.
   Construct and sign the `segment-info-map`, then embed the VSI without changing any hashed bytes or offsets.
   Upload the exact signed bytes as a Media Object using the media storage rules above.
6. Register one Flow Segment for each Media Object with its TAMS timerange and the applicable `init_object_id`. Reuse the init Object while its manifest and key state apply. Register media only after its Objects are uploaded.
7. For this TAMS profile, publish a new signed init Object before a new manifest or session-key state takes effect. Reference it from the first Flow Segment containing media signed under that state, and continue the C2PA sequence across the transition.

For example, sequences 1-4 may reference init Object I0 (manifest M0, key K0), while sequence 5 onward references I1 (manifest M1, key K1). Upload and register I1 before media sequence 5. A new init generation is required when the active manifest or its session-key assertion changes; ordinary decoder-configuration changes also require the corresponding new init data. C2PA also permits updated manifests in media-segment C2PA Manifest Boxes or via `manifestUri`; those delivery options are not part of this TAMS mapping.

TAMS timeranges and VSI sequence numbers are different domains. Preserve and validate both; do not derive one from the other. When `init_segments` is true, every media Flow Segment must reference the Object containing its init segment.

#### Reading and validation

Validation is stateful: a media Object alone does not provide the manifest and public key needed to validate its VSI.

1. Read the Flow and its Flow Segments, following pagination. Check TAMS timeranges and order independently of C2PA sequence order.
2. Read each segment's `init_object.object_id`; `init_object_id` is the registration field.
   When that ID changes, download the init Object using `init_object.get_urls` and validate its C2PA manifest, `moov` binding, session-key assertion, and signer bindings.
   Activate the validated init at the first Flow Segment that references it; do not switch state before processing preceding media or validate dependent media before activating its init.
3. Download each media Object without modifying it. In C2PA sequence order, check the sequence against the expected value and, where used, `mfhd.sequence_number`; check the active `manifestId`; select the key by `kid`; enforce `minSequenceNumber`; and check that the segment's presentation time falls within the key's validity period.
4. Validate the VSI COSE signature and BMFF hash, applying only the matching VSI `emsg` exclusion. Reject validation failures rather than treating them as warnings.
5. Preserve sequence state across init changes with one stateful validator. Do not validate a new generation's media before activating its init, or reset sequence state at the transition. Section 15.5 does not use `previousManifestId`.
6. Report TAMS mapping, segment integrity, signer trust, and stream continuity separately. A valid segment signature does not by itself establish that the credential is trusted or that the TAMS timerange is correct.

The `c2pa-provenance: embedded` tag indicates embedded provenance but does not identify Section 15.4 or 15.5; until profile-specific discovery is standardized, readers need to inspect the media or receive the profile out of band. `manifestUri` was not exercised in the experiment; implementations using it must validate the hashed reference and retrieved manifest ID, and keep the referenced manifest available for as long as the content is served.

### Long-Running Flows

The recommendations in [Application Note 0010](https://github.com/bbc/tams/blob/main/docs/appnotes/0010-long-running-sources-and-flows.md) apply to live C2PA Flows. A validator that follows a growing Flow should persist at least:

* the Flow ID and last validated timerange
* profile-specific continuity state and the last accepted `sequenceNumber` (`streamId` for Section 15.4; active manifest and session-key state for Section 15.5)
* the current init Object ID
* the signer and trust result needed by local policy

On restart, recover enough state to validate the next segment's continuity and key policy. If it cannot be recovered, report continuity as unanchored instead of inventing it. Handle pagination, retention windows, late registration, duplicate delivery, and concurrent reads explicitly.

For an intentionally never-ending service, operational policy also needs to cover secure key storage, sequence and key state recovery without key or sequence reuse, certificate renewal and revalidation, revocation checks, time-stamping, monitoring, checkpoint durability, and what constitutes an announced discontinuity. For Section 15.5, validators should re-check the validity of the claim-signing certificate that authenticated the current session keys. These are deployment concerns beyond merely passing the C2PA wire-format checks.

### Implementation Evidence and Limits

These live recommendations were tested in experimental implementations with video-only CMAF/H.264. The signed Objects were uploaded to and downloaded from a TAMS 8.2 service and validated. The signer and validator used the same unreleased C2PA Rust SDK revision, pinned at commit `8d44625e23794491b312b3984ec49a1b58234a62`. Audio, muxed multi-track media, adaptive bitrate switching, external `manifestUri`, tampered media, replay, unknown or expired keys, and incorrect init mappings were not tested. Before deployment, test rejection of these failures, plus invalid `signerBinding` and revoked signer credentials.
